# Document API

A simple REST API for managing documents, built with FastAPI and SQLite. This project was built as a hands-on learning exercise covering HTTP fundamentals, FastAPI, request/response validation with Pydantic, SQLite persistence, and automated testing with pytest.

## Features

- Full CRUD operations (Create, Read, Update, Delete) for documents
- Request validation using Pydantic models
- Query parameter filtering (filter documents by status)
- Proper HTTP status codes and error handling (404 for missing resources, 422 for validation errors)
- SQLite persistence
- 16 automated tests using pytest and FastAPI's TestClient

## Tech Stack

- **Python 3.14**
- **FastAPI** – web framework
- **Pydantic** – request/response validation
- **SQLite** (`sqlite3` standard library module) – data persistence
- **pytest** + **httpx** – automated testing
- **uvicorn** – ASGI server

## Setup

1. Clone the repository:
   ```bash
   git clone https://github.com/Moeinho/document-api.git
   cd document-api
   ```

2. Create and activate a virtual environment:
   ```bash
   python3 -m venv .venv
   source .venv/bin/activate
   ```

3. Install dependencies:
   ```bash
   pip install -r requirements.txt
   ```

4. Run the server:
   ```bash
   uvicorn main:app --reload
   ```

5. The API will be available at `http://127.0.0.1:8000`. Interactive API docs (Swagger UI) are auto-generated at `http://127.0.0.1:8000/docs`.

## API Endpoints

| Method | Path                    | Description                                  |
|--------|-------------------------|-----------------------------------------------|
| GET    | `/`                     | Health check / welcome message                |
| GET    | `/health`               | Health check                                   |
| POST   | `/documents`            | Create a new document                          |
| GET    | `/documents`            | List all documents (optional `?status=` filter)|
| GET    | `/documents/{id}`       | Get a single document by ID                    |
| PUT    | `/documents/{id}`       | Update a document's title and content          |
| DELETE | `/documents/{id}`       | Delete a document                              |

### Example: Create a document

```bash
curl -X POST http://127.0.0.1:8000/documents \
  -H "Content-Type: application/json" \
  -d '{"title": "My Document", "content": "Some content here"}'
```

### Example: Filter documents by status

```bash
curl "http://127.0.0.1:8000/documents?status=active"
```

### Example: Update a document

```bash
curl -X PUT http://127.0.0.1:8000/documents/1 \
  -H "Content-Type: application/json" \
  -d '{"title": "Updated Title", "content": "Updated content"}'
```

## Data Model

Each document has the following fields:

| Field        | Type   | Notes                                      |
|--------------|--------|---------------------------------------------|
| `id`         | int    | Auto-generated by the database              |
| `title`      | string | Required                                     |
| `content`    | string | Required                                     |
| `created_at` | string | Auto-generated ISO timestamp at creation time|
| `status`     | string | Set to `"active"` by default on creation     |

`id` and `created_at` are always generated server-side and cannot be set by the client, to keep the data consistent and trustworthy.

## Running Tests

```bash
pytest -v
```

The test suite includes 16 tests covering:
- Successful creation, retrieval, update, and deletion of documents
- Validation errors (missing required fields → `422`)
- Not-found errors for GET/PUT/DELETE on non-existent IDs (`404`)
- Query parameter filtering by status
- End-to-end scenarios (e.g. create → delete → confirm it's gone)

Tests run against a separate, temporary SQLite database that is created fresh and deleted after each test run, so they never touch or depend on real project data.

## Design Decisions

This project deliberately keeps scope minimal: no authentication, no frontend, no service-layer abstraction. The focus is a clean, well-tested CRUD API with proper validation and error handling — the fundamentals that any production API needs before additional complexity (auth, external integrations, etc.) is layered on top.
